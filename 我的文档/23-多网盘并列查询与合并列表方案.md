# 多网盘并列查询与合并列表方案

- 状态：**设计稿，未实施**（2026-10-14 确认；2026-10-15 复审修订，见文末「复审修订」与「实施计划」）
- 依赖：[22-网盘浏览与直选上架方案](./22-网盘浏览与直选上架方案.md)、[08-夸克网盘桥](./08-夸克网盘桥.md)、[09-资料池页面与上架编排](./09-资料池页面与上架编排.md)

## 背景与目标

网盘管理现在只连夸克。打开一层目录就调一次 `kuake list`，一行对应夸克里的一个文件。资料池一行也只有一个 `pan_url`，上架卡券只写这一条链接。

接下来同一套目录会同时放在夸克和百度。文件夹名称和目录结构由人工保持一致，但不要求每一份文件两个盘都有。页面要把当前这一层合成一份列表：文件名相同的收成一行，能看出它实际在哪些网盘里。分享和上架只处理真正有这份文件的网盘，把拿到的分享地址写入同一张发货卡券。

以后再接第三个网盘，只增加一种列举和分享实现，列表、合并和卡券沿用同一套规则。

## 关键设计决策

### 1. 打开当前目录时实时查，不维护整盘副本

进入 `/pan-browser?path=/资料/2026` 时，后端对夸克和百度各发一次「列出这个路径」，两次并列执行。合并在内存里完成，列表不落库。

这样做的原因：网盘里新建、删除、改名之后，再进一次这个文件夹就是最新结果。整盘先爬进表再读，会多出一套要同步的副本，分享和上架仍然要当场调 CLI，省不掉慢的那一步。

单次 `kuake list` 大约 0.6–2 秒。两个盘并列后，页面等待时间接近较慢的那一次，而不是两次相加。仍用同步请求加前端 loading，不引入爬取任务。

全库搜索「这个文件在哪个目录」不在本方案里。若以后要做，单独加手动同步索引，网盘管理这一页仍以当场列出的当前目录为准。

### 2. 合并规则

只合并**当前这一层、同一个路径**下的条目。两个盘都查 `/资料/2026`，不跨目录配。

合并键是文件名原文，**不区分大小写**：比较前先做 NFC 归一化，再统一 `lower()` 后比对；展示保留原文。两个 CLI 对同一个中文名的编码可能不同，NFC 必不可少。大小写不同视为同一文件：`A.zip` 和 `a.zip` 收成一行（夸克/百度文件名本身大小写不敏感，同盘无法共存，区分大小写反而会把同一文件拆成两行）。

| 情况 | 结果 |
| --- | --- |
| 两个盘都有 `学军中学2026英语.zip` | 一行，位置里有夸克和百度 |
| 只有百度有 `学军中学2026数学.zip` | 一行，只带百度 |
| 只有夸克有 `学军中学2026物理.zip` | 一行，只带夸克 |
| `A.zip` 与 `a.zip` | 一行（不区分大小写，展示其中一个原名） |
| 同名的文件和文件夹 | 两行，不合并 |
| 同名且都是文件，但大小不同 | 仍是一行，标出「大小不一致」；默认不双盘发货，须人工勾选确认（见 §4） |

某一侧没有这个文件名时，这一侧不出现在该行上，也不显示「缺失」。目录由人工尽量保持一致；暂时只在一个盘里的文件，可以单独浏览、分享和上架。

### 3. 列举失败和「盘里没有」分开

某个盘登录失效或 CLI 报错，是整层查询失败，不是这个文件不在该盘。

- 页面顶部单独标出：哪个盘、失败原因（登录失效、二进制不可用、CLI 报错）。
- 另一个盘查成功的文件照常列出。
- 不能把查询失败理解成「这些文件只在另一个盘」。否则会漏分享。

查成功且这一层没有该文件名，才是真的没有，该盘不写入这一行。

### 4. 分享和上架只处理这一行里已有的网盘

点分享或上架时，遍历该行的 `locations`。有几个盘就分享几个。

- 只有百度：只创建百度分享，卡券只写百度地址。
- 夸克和百度都有：两个都分享，两条地址写入同一张卡券。
- 不要求两个盘同时存在。

一个盘分享失败时，已经成功的链接保留。页面标出失败的那个盘，允许只重试这一侧。两个都失败时不写入资料池，避免一条没有链接的记录。

**大小不一致的保护（2026-10-15 复审新增）**：两个盘同名但大小不同，说明内容很可能不是同一份（如同名不同版本）。这类行**默认不自动双盘分享/上架**：分享和上架弹窗里默认只勾选「单侧存在」或「大小一致」的盘，大小不一致的盘默认不勾选、标红提示，须人工显式勾选才参与。避免把两份不同内容当同一份资料发给买家。

卡券正文按实际拿到的链接逐条写，例如只有百度时：

```text
百度网盘：https://pan.baidu.com/s/xxxx
提取码：abcd

资料：学军中学2026数学.zip
链接失效请联系客服补发。
```

两个都成功时，夸克、百度各一行。没有提取码的盘不写提取码行。

### 5. 一条商品对应多条网盘链接

列表本身是当场合并出来的，不建「目录缓存表」。用户点上架之后，才落一条资料池记录，下面挂多条网盘链接。

现在 `xy_material_pool` 的 `pan_type` / `pan_path` / `pan_url` / `pan_code` / `share_id` / `share_expire_at` 只能表达一个盘，不够再加 `pan_url_2`。新增子表 `xy_material_pool_pan_links`：

| 字段 | 说明 |
| --- | --- |
| pool_id | 所属资料池记录 |
| pan_type | `quark` / `baidu`，以后新盘加新取值 |
| pan_path | 该盘上的完整路径，两个盘结构一致时路径相同 |
| fid | 该盘条目 id，分享查重用 |
| file_size | 该盘上的大小 |
| pan_url / pan_code / share_id / share_expire_at | 这一侧的分享结果 |

同一条资料池记录下，`pan_type` 唯一。再上架同一个路径时，给已有记录补上缺少的那一侧，不另建一条商品。

资料池主记录的身份改为与盘无关的路径：`source_url = pan://<完整路径>`。这样从夸克点上架和从百度点上架命中同一行。已有的 `quark://<路径>` 和爬虫行的 `pan_path` 继续能命中，命中后把新盘链接补进子表，不重复建商品。

主记录上的旧 `pan_*` 字段在过渡期仍代表已有的夸克链接。读卡券时：子表有记录就遍历子表；子表为空就用旧字段，已上架的单盘商品不用迁移也能发货。新导入的多盘记录以子表为准。

### 6. 网盘实现互相独立

每种网盘一个客户端，对外需要四件事：连接状态、列出当前目录、创建分享、**按文件反查已有分享（查重）**。夸克继续用现有 `QuarkPanClient`（查重走 `share-list` 按 `first_fid` 反查）。百度接入时必须提供等价查重能力；若所用 CLI 拿不到等价接口，则在客户端内自建「路径 → 分享链接」查重缓存表兜底，不允许每次上架都新建分享导致分享列表膨胀。

合并、页面和卡券不写具体盘的名字判断。启用的盘放在一份列表里，新增网盘时注册进去即可。

## 运行过程

```text
打开网盘管理，或点进某个文件夹（?path=/资料/2026）
  → 并列：夸克 list 该路径、百度 list 该路径
  → 某一侧整层失败：顶部标出该盘和原因，不把它当成「没有文件」
  → 查成功的条目按文件名原文合并（区分大小写，先做 NFC）
  → 一行只带实际存在的盘；同名文件大小不同则标「大小不一致」
  → 页面表格只渲染这一层

点「分享」
  → 对该行每个 location 调对应盘的分享
  → 弹窗列出每个成功的地址；失败的盘单独标出，可单独重试

点「上架」
  → 弹窗仍补标题、售价、描述、封面（类目仍在资料池上架时再选）
  → 对每个 location 确保有分享链接
  → 至少一条成功：写入或命中一条资料池记录，链接写入子表，状态 pending
  → 全部失败：不落库
  → 资料池审核通过后一键上架，卡券遍历子表里已有的链接
```

文件夹和文件使用同一套合并、列举失败提示和分享规则。文件夹上架仍按 [22-网盘浏览与直选上架方案](./22-网盘浏览与直选上架方案.md) 放在后续，本方案不提前做。

## 后端设计

仍在 `backend-web/app/api/routes/pan_browser.py`，前缀 `/api/v1/pan`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/pan/status` | 每个已启用网盘各查一次连接。返回 `[{pan_type, ok, message}]`。某个盘失败不影响其他盘 |
| GET | `/pan/entries?path=` | 并列列出该路径。返回 `drives`（含失败原因）和合并后的 `list` |
| POST | `/pan/share` | body 带 `locations`。逐个分享，返回每侧的成功链接或错误 |
| POST | `/pan/import` | 按路径命中或新建一条资料池记录，把成功的分享写入子表 |

`GET /pan/entries` 的数据形状：

```json
{
  "path": "/资料/2026",
  "drives": [
    { "pan_type": "quark", "ok": true },
    { "pan_type": "baidu", "ok": false, "error": "登录失效" }
  ],
  "list": [
    {
      "file_name": "学军中学2026数学.zip",
      "dir": false,
      "size_mismatch": false,
      "locations": [
        {
          "pan_type": "baidu",
          "path": "/资料/2026/学军中学2026数学.zip",
          "fid": "123",
          "size": 108000,
          "mtime": 0,
          "pool": null
        }
      ]
    }
  ]
}
```

`locations` 里不补占位。百度这层没列出该文件，这一项里就没有百度。`pool` 仍用来标资料池状态：按 `pan://路径`、旧的 `quark://路径`、以及 `pan_path` 比对，已导入的显示待审核或在售。

`POST /pan/share` 与 `POST /pan/import` 的 `locations` 使用上面同一结构。返回：

```json
{
  "shares": [
    { "pan_type": "baidu", "ok": true, "share_url": "https://pan.baidu.com/s/xxxx", "pan_code": "abcd" },
    { "pan_type": "quark", "ok": false, "error": "创建分享失败" }
  ]
}
```

卡券文本改在 `material_pool_service._build_card_text`：有子表记录就按 `pan_type` 逐条输出；没有子表记录时继续用主记录上的单个 `pan_url`。

## 前端设计

页面仍是面包屑加单层表格，路径继续写在 `/pan-browser?path=...`。技术栈不变。

- 顶部除当前路径外，增加每个盘的连接结果。失败的盘显示原因，成功的盘不额外占一行说明。
- 表格一行一份资料。文件名旁边只列出 `locations` 里的盘名，例如「夸克、百度」或单独「百度」。
- 大小不一致时，在该行显示「大小不一致」，仍允许分享和上架。
- 「分享」弹窗列出本次每个成功盘的链接和提取码，失败盘显示原因和重试。
- 「上架」弹窗展示将要写入的那些盘。提交后若有部分失败，资料池记录保留已成功的链接，并提示哪一个盘需要重试。
- 资料池状态徽章沿用现有含义。多个盘命中同一条资料池记录时，显示这一条的状态，不按盘各显示一个状态。

## 已确认决策（2026-10-14）

1. **数据来源**：打开当前目录时并列查询已启用的网盘，当场合并。不把整盘爬进表再读。
2. **目录**：两个盘使用相同的文件夹名称和目录结构，人工维护，尽量一致。
3. **合并**：文件名原文。比较前做 NFC。文件和文件夹不合并。
4. **显示**：某个盘没有这份文件，该行不显示这个盘，也不显示缺失占位。
5. **分享和上架**：只处理该行实际存在的盘。多个盘的分享地址写入同一条商品的同一张卡券。
6. **查询失败**：登录失效或 CLI 报错在页面顶部单独标出，与「盘里没有这个文件」区分开。
7. **部分失败**：至少一个盘分享成功就可以落库；失败的盘单独重试。全部失败不落库。
8. **扩展**：新网盘实现列举和分享后注册进去，合并与卡券不再改。

## 复审修订（2026-10-15）

针对初稿评审提出的 4 个风险点，决策修订如下：

1. **百度侧能力先行验证**：百度 CLI 的登录稳定性与「创建分享」限制是整个方案的最大外部风险，先于合并逻辑开发做实测（见实施计划阶段 0）。实测不通过则第二阶段暂缓，第一阶段照常交付。
2. **大小不一致默认不双盘发货**：同名文件大小不同的行仍合并展示并标「大小不一致」，但分享/上架弹窗默认不勾选这些盘，须人工显式确认，防止把不同内容当同一份资料发出。
3. **查重列为客户端必备能力**：`PanClient` 协议从三件事扩为四件事，新增「按文件反查已有分享」。百度客户端若无等价 CLI 接口，用自建路径→链接查重缓存兜底。
4. **合并不区分大小写**：比较键为 NFC + `lower()` 后的文件名，展示保留原文（2026-10-14 决策 3 中「区分大小写」作废）。

## 实施计划

按依赖顺序分阶段，每阶段独立可验证，前一阶段不通过不进入下一阶段：

- **阶段 0：百度 CLI 可行性验证（需老板参与）**
  调研并实测候选百度网盘 CLI/自动化方案，验证四件事：登录稳定、列目录、创建分享、分享查重。**需要老板提供百度账号并参与一次扫码/登录验证**。产出：验证结论写入本文档；不通过则停在阶段 1。

  **调研结论（2026-10-15，实测前）**：候选工具为 `qjfoidnh/BaiduPCS-Go`（iikira/BaiduPCS-Go 的活跃维护分支，2026-08 v4.0.2 仍在更新）。文档确认支持：cookie 登录（BDUSS+STOKEN，cookie 方式最稳）、`ls` 列目录、`share set` 创建分享、`share list` 列出已分享（可作为查重依据）、`share cancel` 取消分享。四件事能力齐备，覆盖 §6 协议的四要求。风险残留：百度风控对分享创建频率/账号类型的限制需真实账号实测；备选方案为百度网盘官方 skill（baidu-netdisk-storage，扫码授权）。

  **实测结论（2026-10-15，本机 macOS arm64 v4.0.2，账号「榕树下的榕树2」）**：四件事全部通过——
  1. **登录**：`-cookies="BDUSS=..; STOKEN=.."` 一次成功，登录态持久化在 `~/.config/BaiduPCS-Go`，后续 6+ 次子进程调用全部免登录成功，稳定性满足后端 subprocess 模式；
  2. **列目录**：`ls /路径` 正常，目录/文件、大小、修改时间齐全；
  3. **创建分享**：`share set <路径>` 返回 shareID + 链接 + 提取码（实测创建成功）；支持 `--period 天数`（0=永久，默认永久）与 `-p 自定义提取码`；
  4. **分享查重**：`share list` 返回每条分享的「特征路径」完整网盘路径，**可按路径直接查重，不依赖 fid**（百度 `ls` 不输出 fs_id，`meta <路径>` 可补查单文件 fs_id）。

  **集成注意（实现百度客户端时遵守）**：`ls`/`share list` 输出为人类可读表格，**无 JSON 模式**，需按固定列解析（行首序号、大小列、日期列、名称列，目录名以 `/` 结尾，剔除 `----` 分隔线与「总:」汇总行）。另：该账号网盘 12TB 已用 99.94%，几乎无剩余空间，正式使用前需清理或扩容。
- **阶段 1：协议抽象（纯重构）**

  新增 `xy_material_pool_pan_links` 模型与建表迁移（`(pool_id, pan_type)` 唯一）。验证：迁移脚本执行成功、旧数据无感。
- **阶段 3：后端接口**
  改造 `/pan/entries`（并列合并、失败分级、大小写不敏感合并键）、`/pan/share`（逐盘分享+查重）、`/pan/import`（命中补链）。验证：单盘（仅夸克）行为与现状完全一致。
- **阶段 4：卡券文本**
