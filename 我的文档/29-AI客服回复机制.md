# AI 客服自动回复机制

- 状态：**已实施**（2026-11-05，本机 py_compile + tsc 通过；待线上验证效果）
- 2026-11-09 更新：商品描述解析链（本地表五级兜底）、AI Prompt 快照落库、管理页"详情"弹窗（见文末两节）
- 涉及提交：`1da389d`、`9f0a998`、`f5514a7`、`7465160`、`93a690a`

## 本文档解决什么

闲鱼买家发来消息时，由大模型自动生成客服回复。本文档记录这套功能的**整体架构、提示词分层体系、配置维护入口和关键机制**，作为后续维护、调优、排障的依据。上游原版 README 只有一句话介绍，无设计文档。

业务范围：全部为**虚拟资料（电子版）**，百度网盘 + 夸克网盘双盘发货，无物流无邮费。**不支持议价**（一口价政策）。

## 消息处理主链路

```
买家消息（闲鱼 WebSocket，websocket 服务）
   │
   ▼
auto_reply_service.handle_chat_message      ← 路由与兜底，不做"智能"
   自己发的消息 → 触发人工介入暂停
   系统消息 / 自动发货触发 → 跳过回复
   商品归属校验 → 去重 → 过滤词
   │
   ▼
get_reply 优先级：关键词规则 ──► AI 回复 ──► 默认回复 ──► 静默
   │
   ▼
ai_reply_engine.generate_reply              ← 智能发生的地方
   组装分层提示词 → 调大模型 → 双方消息入库
   │
   ▼
xy_ai_chat_messages（对话上下文）  xy_auto_reply_logs（决策日志）
```

## 提示词分层体系（核心设计）

发给模型的是 `[system, user]` 两条消息，system 按以下顺序拼装：

| 层 | 内容 | 来源 | 维护入口 |
| --- | --- | --- | --- |
| 统一话术 | 身份（虚拟资料店铺客服）+ 三种情境策略（砍价/问内容/日常）+ 示例 | 引擎内置 `default_prompts["unified"]` | 账号 AI设置 → 高级设置「统一话术覆盖」（unified key） |
| T1 全局规则 | 6 条红线：一口价、不编造、不承诺做不到的操作、不引导站外、诚实承认自动客服身份、复杂问题转人工 | 引擎内置，强制追加 | 改代码 |
| T2 店铺说明 | 虚拟商品/双网盘/无物流/补发售后等业务事实 | `ai_reply_settings.shop_prompt`，**带默认值** | 账号 AI设置 → 店铺说明（主配置入口） |
| T1+ 自定义规则 | 账号级 `_global` key，追加在系统规则之后 | `ai_reply_settings.custom_prompts` JSON | 高级设置「全店通用规则」 |
| L3a 商品档案 | 标题(120字)/价格/描述(2000字)，自动注入 | 商品库 `xy_catalog_items`；描述走**本地表五级解析链**（见下节） | 零维护 |
| L3c 商品补充 | 卖点/FAQ/格式/网盘说明等增量知识，注入为「商品特殊说明」 | `xy_catalog_items.ai_prompt` | 商品管理 → AI提示词（单条/批量） |
| L4 对话历史 | 最近 10 条，注明 assistant 为客服本人回复 | 自动从 `xy_ai_chat_messages` 取 | 零维护 |
| L5 输出约束 | 只输出最终回复、≤80 字、temperature 0.3 | 引擎内置 | 改代码 |

要点：**规则和知识在进模型前分层拼装好，模型只负责"说话"；红线在系统层强制注入，任何自定义内容都压不住它。**

## 商品描述解析链（2026-11-09）

**背景**：商品同步入库的 `metadata_json.detail` 来自卖家平台商品列表接口，该接口**不返回商品描述文字**；且提取逻辑对空 `detail_params: {}` 会误判为"暂无商品描述"，导致目录/卖点/文件格式等信息完全进不了 AI 上下文。

**方案**（`auto_reply_service._resolve_item_description`）：只查本地业务表，不调用闲鱼接口，按以下优先级逐级兜底，任一级命中即返回；全部落空才用空描述，绝不影响 AI 回复主流程：

| 优先级 | 数据源 | 说明 |
| --- | --- | --- |
| 1 | 商品 `metadata_json.description` | 历史回写的持久化缓存 |
| 2 | 商品 `metadata_json.detail` | 同步详情 JSON 中的**显式描述字段**（`description`/`desc`/`item_description`/`itemDesc`/`content`）；标题兜底不算命中，避免拦截后续真正的来源 |
| 3 | 资料池 `xy_material_pool` | 上架流水线按 `account_id + item_id` 回填的 `description`（资料池上架的商品这一步即命中） |
| 4 | 发布日志 `xy_publish_logs` | 该商品最近一次成功发布的 `description` |
| 5 | 素材库 `xy_product_materials` | 发布日志 `material_id` 关联的宝贝描述 |

实际命中来源会写运行日志（`商品描述取自资料池/发布日志/素材库`），便于核对。

## Prompt 快照与排查工具（2026-11-09）

**问题**：此前"真实发给模型的完整提示词"只存在于运行日志，不落库，AI 回复不及预期时无法事后还原输入。

**方案**：

1. **落库**：`xy_auto_reply_message_logs` 新增 `prompt_snapshot` JSON 列（建表 + `COLUMN_MIGRATIONS` 自动迁移），在调用模型**之前**由 `ai_reply_engine.generate_reply` 填充，调用失败也留有快照。内容包含：
   - `system_prompt` / `user_prompt` / `messages`（逻辑层完整请求）
   - `request_messages`（按服务商协议实际组装的请求，OpenAI 兼容含追加的"直接回复规则"）
   - `shop_prompt` / `default_shop_prompt_used` / `custom_global_rules`（规则来源）
   - `item_info` / `context_injected` / `buyer_message`（事实层）
   - `provider_type` / `provider_name` / `model_name`（**不含 api_key**）
2. **详情接口**：`GET /api/v1/auto-reply-logs/{log_id}`（带 owner 权限校验，管理员可看全部），返回完整日志 + `prompt_snapshot` + `context_snapshot`。
3. **管理页弹窗**：消息日志页每行新增"详情"按钮（`AutoReplyLogDetailModal`），分"基本信息 / 对话内容 / AI 提示词快照"三板块展示，提示词区块支持一键复制；`context_snapshot.ai_prompt_snapshot` 另存提示词长度与模型摘要，避免列表加载大字段。

分析 SQL 示例：

```sql
SELECT prompt_snapshot, reply_text, error_message
FROM xy_auto_reply_message_logs
WHERE reply_strategy = 'ai' AND id = <日志ID>;
```

## 关键机制

| 机制 | 说明 |
| --- | --- |
| 一口价政策 | 全局规则第 1 条 + 店铺说明兜底；AI 口头报价与改价动作无联动（程序不改价），故禁止任何承诺 |
| 人工介入暂停 | 卖家手动回复后，自动暂停该会话（或按买家+商品维度）AI 回复，默认 10 分钟，可配 |
| 6 秒新消息去重 + 会话锁 | 买家连发消息只回最新一条；同一会话串行处理防并发 |
| 消息入库 | 双方消息写 `xy_ai_chat_messages`（上下文来源）；人工暂停期间/AI 未启用时的消息不入库，上下文会缺段。**卖家人工回复也不进该表**，AI 的对话历史里看不到人工插话 |
| Prompt 快照 | 每次 AI 回复前，真实发给模型的完整提示词写 `xy_auto_reply_message_logs.prompt_snapshot`（JSON），调用失败也留存，详见上节 |
| 模型调用 | OpenAI 兼容（4 种降级重试）/ DashScope 应用 / Gemini / Anthropic；超时 30s；空回复/截断有重试 |
| AI 失败降级 | 生成失败或返回空 → 落默认回复 → 都没有则静默（日志可查原因） |
| 已下单用户开关 | `ai_reply_block_ordered_users`：有订单的买家跳过 AI |

## 历史演进（为什么这么改）

| 原设计 | 现状 | 原因 |
| --- | --- | --- |
| 议价功能（砍价话术、递减优惠、议价轮数限制、最大折扣配置） | **全部移除** | AI 只口头报价、程序不改价，链路断裂；口头承诺无法兑现有纠纷风险 → 改一口价 |
| 关键词意图分类（price/tech/default 本地匹配） | **移除**，情境判断交给模型 | 预 LLM 时代的遗留设计；"刀""还能"等子串误命中；全局规则兜底后误判无害 |
| 一套提示词 JSON 手填 | 分框可视化编辑 + 系统默认可查看 | JSON 手填易错；留空即用默认 |
| "绝不透露是 AI" | 诚实承认自动客服身份 | 参考成熟实践：冒充真人被戳穿伤信任且有平台风险 |
| 商品描述截断 800 字 / 回复上限 40 字 / temperature 0.5-0.7 | 2000 字 / 80 字 / 0.3 | 资料类商品描述长；40 字说不清；客服要稳定口径不要创意 |
| 商品描述取 `metadata_json.detail` 直接注入（2026-11-09 前） | **本地表五级解析链**（商品 metadata → 资料池 → 发布日志 → 素材库） | 卖家平台列表接口不返回描述文字，AI 上下文"商品描述: 暂无商品描述"，目录/文件格式缺失 |
| 完整提示词只在运行日志（2026-11-09 前） | **`xy_auto_reply_message_logs.prompt_snapshot` 落库** + 管理页"详情"弹窗 | 回复不及预期时无法事后还原输入，排障靠翻日志文件 |

## 已知边界与注意事项

1. **商品信息依赖商品库同步**：商品不在 `xy_catalog_items` 时，AI 只能拿到"商品信息获取失败"，答非所问——先查商品同步。描述文字已通过本地表五级解析链兜底（见上节），但商品记录本身缺失时无解。
2. **议价相关设置字段**在后端 schema/引擎默认值中仍保留（兼容旧数据），前端已移除，均为死配置。
3. **意图统计归零**：`xy_ai_chat_messages.intent` 不再写入，后台议价统计恒为 0（历史数据保留）。
4. **移动端自定义提示词输入框是原始文本**（非 JSON），引擎解析失败静默忽略——该字段在移动端实际无效，待修。
5. **prompt 约束是概率性的**：极弱模型仍可能失守红线，换模型或加强 `_global` 措辞。
6. 修改引擎内置文案（统一话术/全局规则/默认店铺说明）需**同步三处**：`ai_reply_engine.py`、`ai_reply_service.py` 的 DEFAULT_AI_SETTINGS、`Accounts.tsx` 的 SYSTEM_DEFAULT_PROMPTS，注释中已互相标注。
7. **历史数据无快照**：`prompt_snapshot` 为 2026-11-09 新增，之前的日志该字段为 NULL，属正常现象。

## 调优闭环

上线后每周从 `xy_ai_chat_messages` 抽 AI 回复挑毛病，归类后补到对应层：
答错商品事实 → 补商品 AI提示词；说了不该说的 → 补全局规则/`_global`；某类问题话术差 → 改统一话术；啰嗦/格式乱 → 调输出约束。改完重启 websocket 验证。

**排障首选"详情"弹窗**（消息日志页 → 详情）：对照当次回复与 `prompt_snapshot` 里的 system prompt（规则层）和 user prompt（商品信息/对话历史/买家消息），可直接定位"规则没生效 / 商品信息没注入 / 上下文缺段"三类问题；配合 `商品信息构建完成` 运行日志核对描述解析链走了哪一级。
