# 资料池分享修复与实际在售状态对账

- 状态：**已实施并真实数据验证**（2026-11-05/06，macOS 本机）
- 依赖：[22-网盘浏览与直选上架](./22-网盘浏览与直选上架方案.md)、[23-多网盘并列查询与合并列表](./23-多网盘并列查询与合并列表方案.md)、[27-网盘互传同步方案](./27-网盘互传同步方案.md)、[13-自动续售链路](./13-自动续售链路.md)
- 涉及提交：`7d2a7f7`

## 本文档解决什么

两件事：

1. **百度网盘分享静默错配**：网盘管理里对百度盘发起分享，没成功也没报错，资料池里 baidu 行的链接却是夸克地址（事发记录：资料池 ID 20）；
2. **资料池状态失真**：一键上架成功后 status 永远停在 `listed`，商品卖出、下架、删除后资料池仍显示"在售"，无法区分，且这类记录既不能重新上架也不能重新审核（卡死）。

## 第一部分：分享错配根因与修复

### 根因

分享链路 `POST /pan/share` → `_ensure_share_for_location`（`backend-web/app/api/routes/pan_browser.py`）第一步"复用已有分享"的查重函数 `_find_pool_by_pan_path` **只比路径、不比网盘类型**。

网盘互传同步后两个盘路径完全相同，给百度位置发起分享时按 `pan_path` 命中了夸克侧的主记录，把夸克链接原样返回并贴上 `pan_type=baidu` 标签，入池时写进 baidu 子表行。全程**无异常、无日志**，`create_share` 根本没执行——所以看不到任何报错。`pan_sync_log` 只记互传任务，不记分享创建。

### 修复（三层）

1. **根因**：`_find_pool_by_pan_path` 增加 `MaterialPool.pan_type == pan_type` 条件；两处复用分支补 `logger.info`；
2. **兜底**：新增 `_validate_share_url`，所有分享结果返回前校验域名（baidu 必须 `pan.baidu.com`、quark 必须 `pan.quark.cn`），不匹配抛错按"该盘分享失败"处理，错配不再静默写库；
3. **存量数据**：事发记录 baidu 子表行直接用后端环境调 `BaiduPCS-Go share set` 重建真实分享并写回。

### 重新分享（新功能）

资料池行内新增「重新分享」按钮（入池过的记录显示）：

- `POST /material-pool/{id}/reshare`：对子表所有网盘位置**强制新建分享**（不走复用查重），域名校验后写回子表；逐盘返回结果，单侧失败可重试，不拖垮其他盘；
- 前端确认弹窗 + 逐盘结果反馈（成功提示 / 每盘独立错误）。

与网盘管理页「补链入池」的关系：补链入池解决"**缺某个盘**"（已有记录上加链接）；重新分享解决"**链接失效或错配**"（对已有位置重建覆盖）。

## 第二部分：商品实际在售状态对账

### 设计定位（两条已定稿决策）

- 状态是**运营参考，不追求 100% 准确**，不准也不会有大问题；
- **不直接调用闲鱼接口**核对（账号风控等未知问题），纯数据库比对。

### 为什么是两个状态而不是一个

`status`（流水线）回答"资料走到哪一步"，由业务流程不可逆推进（crawled→…→listed）；`item_live_status`（实际在售）回答"商品还在不在卖"，由对账任务来回改（售出→已下架→续售→在售）。合并成一个字段会语义打架、状态机被对账搅乱。数据层保持两个正交字段，**前端展示层合并为一个组合徽章**：

| 展示 | 含义 |
| --- | --- |
| 绿色「在售」 | listed + 对账确认商品真实在卖 |
| 红色「已下架」 | listed + 关联商品已不在目录（悬停提示可重新上架） |
| 靛色「在售·待核对」 | listed + 对账尚未覆盖（每小时自动核对） |
| 其他 | 走原流水线徽章（待审核/审核通过/失败…） |

### 判据：卡券链路，不是 pool.item_id

续售是**重新发布全新商品**（`auto_relist_task.py` 拿到全新 item_id），关联迁移（`relist_association_migration_service.py`）会把新 item_id **追加到卡券关系 `CardItemRelation`**，但**没有任何环节回写 `xy_material_pool.item_id` 和素材库 `current_item_id`**——这两个指针永远停在已卖出的旧商品上。

因此判据走卡券链路（唯一被续售主动维护、且挂在资料池记录上的关联，含失败重试最终一致）：

```
pool.card_id → xy_card_item_relations 的全部 item_id
  → 至少一个仍存在于 xy_catalog_items → 在售
  → 全部不在目录 → 不在售
```

- 「不在售」涵盖售出待续售、手动下架、删除（虚拟商品默认续售，售出是过渡态，续售重发后新商品入目录自动回到在售，不单独区分"已售出"）；
- `pool.card_id` 为空或卡券无关联记录时，退回 `pool.item_id` 兜底比对（兼容旧数据）；
- 目录本身只增量同步在售商品、不主动清理下架数据，"在售"是近似判定，偏差最多一轮对账。

**真实数据验证**：pool 9 原商品已不在目录，但卡券关系里的续售新商品在目录 → 正确判"在售"；旧版（用 pool.item_id）会永久误报"已下架"。

### 两个同步通道

1. **定时对账**：scheduler 任务 `material_pool_live`，默认每小时（纯 DB 比对，无接口风险），一轮一次目录查询逐条回写，幂等。已在调度器全点位注册（scheduled_task_service / scheduler_service 六处 / internal.py 触发白名单 / init_database 种子），管理页可改间隔与启停、可手动触发；
2. **手动刷新**：`POST /material-pool/{id}/refresh-item-status` + 资料池行内「核对在售」按钮（紫色，即时返回）。

### 数据层

`xy_material_pool` 新增三列（模型 + 建表 DDL + `COLUMN_MIGRATIONS` 存量迁移）：

| 列 | 说明 |
| --- | --- |
| `item_live_status` | `on_sale` / `off_sale` / `unknown`（默认 unknown） |
| `item_live_checked_at` | 上次核对时间 |
| `item_live_error` | 最近核对说明（不在售原因等） |

列表接口 `_row_to_dict` 输出三列，`GET /material-pool` 支持 `item_live_status` 筛选（前端「实际在售」下拉，可一把捞出"显示在售但实际已下架"的幽灵商品）。

核心代码：`common/services/material_pool_live_status.py`（scheduler 与 backend-web 共用）。
