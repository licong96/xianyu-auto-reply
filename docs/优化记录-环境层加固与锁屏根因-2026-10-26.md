## 3. 保持登录的实现机制（代码梳理）

四层体系，围绕 **Cookie + IM Token** 两件东西：

1. **Cookie 保活**：`api_cookie_renew`（1 小时/次，接口方式，主力）；
   `cookies_refresh`（浏览器方式，已禁用）；`login_renew`（10 分钟/次，已禁用）。
   Session 真过期时触发后台密码登录兜底。
2. **scheduler 侧 Token 预续期**：每 120 秒扫库，给 1 小时内到期的 Token 预取，
   命中风控则委托 websocket 过滑块后重试。
3. **websocket 侧 Token 维护**：
   - 缓存优先（命中即用，不调用接口）；
   - 例行刷新循环每 72000 秒（20 小时），失败 7200 秒（2 小时）后重试；
   - **Cookie 刷新循环每 60 秒检查、每 180 秒实际刷新一次**（收到消息后 5 分钟冷却）；
   - 心跳每 15 秒，连接本身存活即登录有效的最直接信号。
4. **风控判定口径**（`common/services/captcha/token_response.py`）：
   Token 接口返回的 `ret` 文本命中即视为风控——`FAIL_SYS_USER_VALIDATE`、
   `RGV587_ERROR`、`哎哟喂,被挤爆啦`、`挤爆了`、`punish?x5secdata`、`captcha` 等。

**检测频率结论**：现有频率合理，不建议再加密——正常状态下缓存命中根本不碰接口；
真正的问题不在检测频率，而在**失败时的无退避重试**（10-20 把间隔从 20s 调到 120s 的结论依然成立）。

## 5. 关键认知（已验证，纠正了常见误解）

1. **机器 24 小时保持会话从未失败**——服务从 10-21 持续在线，问题从来不在会话存续。
2. **显示器与锁屏无关**：锁屏逻辑不检测显示器；真显示器对锁屏问题零改善。
3. **HDMI 欺骗器有效且必需**：作用是维持 GPU 输出、让控制台会话有桌面可渲染
   （无显示设备时部分 GPU 停渲染）。插着它是对的，无需真显示器。
4. **「锁屏记录」≠「不能滑块」**：10-23 18:19 锁定后至 10-26 10:33 期间，
   因物理控制台会话在线握着交互桌面，凌晨 04:48、08:27 滑块仍成功。
   真正危险的状态是「**没有任何会话持有交互桌面**」。
5. **`powercfg /requests` 检测不了锁屏**：它列的是"电源请求占用"
   （谁在阻止睡眠/关屏），与锁屏状态无关。实测本机仅 Kimi.exe 持有 EXECUTION 请求。
6. **权威检测 API**：`OpenInputDesktop()` + `GetUserObjectInformation(UOI_NAME)`——
   返回 `Default`=可交互、`Winlogon`=已锁。已在本机实测（当前 = Default）。
   备选：按会话查 logonui 进程；`quser` 看会话 Active/Disc。
7. **RDP 断开即锁是客户端侧触发**：tscon 技巧（见 7.2）可把会话移交物理控制台规避。

## 6. 错误率高的原因排序

1. **环境根因**：会话锁屏/断开导致 real_mouse 前台激活必失败（今日 ~100%）。
2. **失败不后退、无退避**：real_mouse 失败不回退 + 远程通道封锁，环境不可交互时每次注定失败。
3. **多环路重试风暴**：scheduler（120s）+ websocket Cookie 刷新循环（180s）双路并发打
   Token 接口；scheduler 候选排除只看 `processing_status='processing'`，
   失败账号每轮照样重试。高频失败又延长风控时长，形成正反馈。
4. 正面因素：10-21 上线的通知链路已生效（scheduler 1 小时冷却、websocket 3 小时冷却）。

### 7.2 tscon 机制说明（评估结论：真实有效，适合本机）

`tscon %sessionname% /dest:console` 把当前远程会话原样移交物理控制台再断开。
对本机的特殊价值：服务与滑块窗口都在会话 1，tscon 后会话 1 自己变成控制台会话，
获得"欺骗器所代表的物理控制台"这个持久交互桌面。
边界：每次断开都要执行（人工仪式）；下次 RDP 连入会抢回会话；机器重启后归零
（靠 A1 自动恢复）；控制台保持解锁有物理安全代价（无头可信环境可接受）。

### 7.3 方案 B：环境失败检测 + 指数退避（第 2 步，待实施）

- **B1** 新增 `common/services/captcha/desktop_env.py`：
  `get_input_desktop_name()` / `is_interactive_desktop()`（OpenInputDesktop 为主，
  WTS 会话状态双保险；非 Windows 直接判不可用）。
- **B2** 失败分类：`real_mouse_slider._ensure_window_foreground` 失败抛
  `EnvNotInteractiveError`；`run_real_mouse_verification` 返回 ENV_UNAVAILABLE 哨兵
  （仿 URL_EXPIRED 先例）；orchestrator 透传第三返回值，现有调用方不受影响。
- **B3** 每账号退避状态机：档位 3/10/30/60 分钟封顶，Redis+内存双份（双进程共享），
  成功或环境恢复归零；配置化 `captcha.env_check_enabled`、
  `captcha.env_backoff_tiers`（新 key，无 DDL，改库热生效）。
- **B4** 接入点：websocket `token_manager.cookie_refresh_loop`（刷新前探测，
  不可用则跳过本轮、完全不碰 Token 接口）；`cookie_token_manager` 滑块失败分支
  （风控日志打「环境不可用」标记 + 新通知类型 `env_not_interactive`，3 小时冷却）；
  scheduler `token_renewal_task._load_candidates`（排除处于环境退避期的账号）。
- **B5** 通知文案附处理指引。
- 预期收益：今天这种 3 小时 100 次失败压到 ≤10 次，且无效请求减少后风控更快解除。
