# 设计方案：网盘分享自动续期与内容存活巡检

- 日期：2026-11-06
- 状态：待评审 / 待开发
- 涉及范围：backend-web、scheduler、common、frontend

---

## 1. 背景与目标

资料池（`xy_material_pool` / `xy_material_pool_pan_links`）中的网盘分享地址默认 30 天有效期（`KUAKE_SHARE_DAYS`）。地址过期或被删除后，已绑定卡券（`xy_cards.text_content`）中保存的仍是旧地址，买家拿到的就是死链。

**目标：**

1. **自动续期**：分享地址到期前 7 天，自动重新创建分享，拿到新地址，并同步更新所有使用旧地址的地方（卡券 `text_content`）。
2. **内容存活巡检**：用真实浏览器定期打开在售商品对应的分享地址，判断页面能否打开、内容是否存在；**只做日志记录和消息通知，不做任何自动处理**，是否失效由人工判断。
3. **续期后验证**：每次创建新分享地址后，自动触发一次页面检查，验证新地址健康，结果记入日志。

**非目标（明确不做）：**

- 不做新的"创建分享"功能——完全复用资料池现有的重新分享能力（`POST /material-pool/{pool_id}/reshare`）。
- 巡检发现异常时**不自动重新分享**，只记录日志 + 通知，人工介入。
- 不做百度/夸克网盘内的文件位置迁移；方案前提是网盘内 `pan_path` 保持不变。

## 2. 关键事实与设计依据

调研代码后确认的事实：

| 事实 | 设计依据 |
|---|---|
| 重新分享已实现：`material_pool.py` 的 `reshare_pool()`，按 `pan_path` 调网盘 CLI（kuake_cli / BaiduPCS-Go）重建分享，写回 `pan_url / pan_code / share_id / share_expire_at` | 续期 = 调度现有能力，零新分享代码 |
| `xy_material_pool_pan_links` 已有 `fid`、`share_id`、`share_expire_at` 字段（注释即写明"撤销/巡检用"） | 只需新增巡检状态字段，无需大改 |
| 卡券发货是**发货时实时读** `xy_cards.text_content`（websocket 自动发货、提货均如此） | 续期后重建 `text_content` 一处即全部生效 |
| `_build_card_text()` 目前在 `MaterialPoolService` 上，scheduler 引不到 | 需抽到 `common/services/`（项目既有模式，参照 `material_pool_live_status.py`） |
| scheduler 无法 import backend-web 的 pan client | scheduler 通过 HTTP 调 backend-web 内部接口（既有模式：`http_client.py` + `internal_auth`） |
| 日志体系成熟：`xy_pan_sync_logs` 模型 + `pan_sync_logs` 路由 + `panSyncLogs` 前端页 | 新日志表照此模式三件套 |
| 项目内无现成"打开分享页验证"代码；`quark-模拟代码/link_validator.py` 是 DrissionPage + 选择器探测的成熟参考 | 巡检服务借鉴其做法，重写为针对资料池表 |

**关于新旧地址共存**：夸克/百度的"重新分享"创建的是全新分享关系，旧地址在其有效期内仍可正常访问，新旧地址不冲突、无切换空窗。因此续期阈值取 7 天：即使买家在续期前一刻下单，拿到的地址也至少还有 7 天有效期。

## 3. 总体架构

```
scheduler 任务A「分享到期续期」（每 12 小时）
  扫描 xy_material_pool_pan_links：
    share_expire_at <= NOW() + 7 天
    AND 所属资料池有在售商品（pool.status='listed' 且 card_id 不为空）
        │
        ▼ HTTP（internal auth）
  backend-web 内部接口 POST /internal/material-pool/reshare-expiring
    ① 复用现有 reshare 逻辑，对每条链接重建分享
    ② 写回 pan_links：pan_url/pan_code/share_id/share_expire_at/last_renew_at
    ③ 重建 xy_cards.text_content（卡券立即指向新地址）
    ④ 把新地址写入「待巡检队列」
        │
        ▼
scheduler 任务B「内容存活巡检」（每天，增量批次）
  按 last_check_at 升序取一批（默认 50 条）
  DrissionPage 真实浏览器逐条打开 pan_url
  判定 valid / invalid / empty / error（风控另判）
  写 last_check_status / last_check_at + 日志表
  invalid / error → 仅日志 + 消息通知人工，不做其他动作
  （待巡检队列中的新地址优先插队检查）
```

**职责边界**：续期任务负责"写"，巡检任务负责"读和判定"，巡检**永不触发续期**。

## 4. 模块设计

### 4.1 到期自动续期

#### 调度

- 新任务 `share_renew_task`，仿照 `scheduler/app/services/scheduler/material_pool_live_task.py` 的写法：薄封装、`async execute()` 开 `async_session_maker` 会话、业务逻辑放 `common/services/`。
- 三处注册点：`scheduled_task_service.py`（`TASK_CODE_SHARE_RENEW` + `DEFAULT_CONFIGS`，默认 `interval_seconds=43200`）、`scheduler_service.py`（循环 + 手动触发分支 + 状态条目）。
- 也可在 `xy_scheduled_tasks` 配置表中调整间隔、启停，复用现有任务配置界面。

#### 筛选 SQL（核心条件）

```sql
SELECT l.*
FROM xy_material_pool_pan_links l
JOIN xy_material_pool p ON p.id = l.pool_id
WHERE l.share_expire_at IS NOT NULL
  AND l.share_expire_at <= NOW() + INTERVAL 7 DAY
  AND p.status = 'listed'
  AND p.card_id IS NOT NULL
  AND p.is_deleted = 0
ORDER BY l.share_expire_at
LIMIT 200;   -- 单轮上限，防止一轮触发过多网盘操作
```

#### 执行链路（backend-web 内部接口内）

`POST /internal/material-pool/reshare-expiring`（`require_internal_auth`）：

1. 接收 scheduler 传来的 link id 列表（或自己按上面的条件查询）；
2. 对每条 link：`make_client(link.pan_type).create_share(link.pan_path, days=_share_days(), passcode=False)`——**这就是现有 reshare 的逻辑，提取复用，不重写**；
3. 域名一致性校验沿用 `_validate_share_url()`；
4. 更新 link 行：`pan_url / pan_code / share_id / share_expire_at / last_renew_at`；主行 legacy `pan_*` 字段在 `pan_type+pan_path` 匹配时同步刷新（沿用 reshare 现有行为）；
5. **重建卡券**：调用抽取后的 `common/services/card_share_text.py: build_card_text(session, pool_id)`，更新 `xy_cards.text_content`（仅当卡券当前内容仍引用旧地址时，避免覆盖人工改过的卡券）；
6. 将新地址写入待巡检队列（见 4.2）；
7. 全程写日志表（见 4.3），任一条失败不影响其他条，失败原因记 `fail_reason`。

#### 失败分支

| 场景 | 处理 |
|---|---|
| CLI 返回路径不存在（源文件被删） | 标记该 link，日志 + 通知人工补资源，**不再自动重试** |
| 创建分享失败（弹窗/网络/CLI 异常） | 下轮续期任务自动重带（7 天窗口内天然有多次机会），连续 3 轮失败 → 通知人工 |
| 单轮触发量超限 | LIMIT 截断 + 日志注明"本轮截断，余下下轮处理"，避免网盘风控 |

### 4.2 内容存活巡检（只读 + 通知）

#### 服务位置与浏览器管理

- 新服务 `common/services/share_health_check.py`，同时被 scheduler 任务和 backend-web（续期后的即时检查）调用——放 `common/` 是项目既定模式。
- 浏览器管理：借鉴 `quark-模拟代码/browser.py`——DrissionPage Chromium，**独立调试端口 + 独立 `user_data_dir`**（与其他用途的浏览器实例隔离），脚本结束 `browser.quit()`。夸克、百度共用这一个实例（不同域名），同域名严格串行。

#### 单条检查状态机（总预算 15 秒）

```
deadline = now + 15s
① tab.get(url, timeout=15)
   超时 → 判 error（网络问题，不是链接失效）
② 在 deadline 前轮询"错误容器"（每次 tab.ele(选择器, timeout=剩余秒数)）：
   百度: css:#error-new #shareError
   夸克: 失效文案容器（关键字"分享已过期/文件已被删除/你来晚了"）
   命中 → 判 invalid，记录命中文案
③ deadline 前未命中错误容器，查"有效容器"：
   夸克: css:tbody.ant-table-tbody（需行数 > 0）
   百度: css:div.file-name
   命中 → 顺手抓"共 N 个文件"文本：N≥1 判 valid；N=0 判 empty
④ deadline 到、两个容器都没出现：
   再看 URL/文本特征判断是否登录墙/验证码/风控页
   命中风控特征 → 暂停巡检任务 30 分钟 + 通知
   否则 → 判 error，进重试队列
```

**DrissionPage 要点**：

1. 夸克分享页是 Vue SPA，`load` 事件触发时列表常未渲染，**必须等选择器出现而不是等 load 事件**；`tab.ele(selector, timeout=N)` 自带轮询，返回 `None` 只代表"N 秒内未出现"。
2. `tab.get(url, timeout=15)` 超时不会抛异常而是带着不完整页面继续，超时时长要算进 15 秒总预算，不能叠加成 30 秒。
3. 每次检查**记录命中的选择器名、页面标题、关键文本片段**，便于网盘改版后快速定位要改的选择器。

#### 节奏与限速（防风控）

- 每条检查完，**随机等待 2~3 秒**（`random.uniform(2, 3)`）再开下一条；
- 单批默认 50 条，按 `last_check_at` 升序取（最久未查优先），天然摊平全天；
- **插队机制**：续期任务产生的新地址进入待巡检队列（可用 Redis 或一张临时队列表，建议简单起见用内存 + 数据库标记 `check_priority=1`），10 分钟内必查；
- error 地址当天重试不超过 3 次，仍 error 则当天不再查，记日志通知人工。

#### 误判保护（轻量版）

巡检只记录、不动作，误判成本低，因此不需要复杂的 suspect 状态机，只做一件事：**invalid 判定后再复查一次**（间隔 30 分钟、换一轮重新打开），两次均 invalid 才发通知并记 `last_check_status='invalid'`；单次命中先记日志不通知。这样能把登录态过期、瞬时网络抖动这类高频误报挡在通知之外。

#### 人工处理入口（配套）

- 通知消息中带上资料池记录链接和管理页跳转，人工确认后：在资料池页面手动点"重新分享"（现有功能）即可完成修复——续期链路会把卡券一并更新。不需要为此开发新的人工操作功能。

### 4.3 日志与通知

#### 日志表 `xy_share_check_logs`

仿 `xy_pan_sync_logs` 模式（模型 `common/models/share_check_log.py` + 路由 `backend-web/app/api/routes/share_check_logs.py` + 前端页 `frontend/src/pages/shareCheckLogs/`），字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT PK | |
| task_type | VARCHAR(20) | `renew`（续期）/ `check`（巡检） |
| pool_id | BIGINT | 资料池记录 ID |
| pan_type | VARCHAR(20) | quark/baidu |
| pan_url | VARCHAR(500) | 检查/续期的地址（续期时记新地址） |
| old_url | VARCHAR(500) NULL | 仅续期：旧地址 |
| result | VARCHAR(20) | renew：done/failed；check：valid/invalid/empty/error |
| detail | TEXT | 命中的选择器、页面标题、错误文案、CLI 错误信息等 |
| fail_reason | VARCHAR(500) NULL | 失败原因 |
| duration_seconds | FLOAT | 单条耗时 |
| created_at | DATETIME | |

每次任务结束另输出一行汇总日志（检查 N 条、valid X、invalid Y、error Z、续期成功 A、失败 B）。

#### 通知

- invalid（复查确认后）、error 连续 3 次、源文件不存在、触发风控暂停——四类事件发通知；
- 通知渠道复用项目现有机制（以项目当前的通知实现为准，如站内通知或群机器人），消息带 `pool_id`、资源名、地址、判定结果，可一键跳到资料池处理。

## 5. 数据库变更

### 5.1 `xy_material_pool_pan_links` 新增字段

```sql
ALTER TABLE xy_material_pool_pan_links
  ADD COLUMN last_check_status VARCHAR(20) NULL COMMENT '巡检状态：valid/invalid/empty/error' AFTER share_expire_at,
  ADD COLUMN last_check_at DATETIME NULL COMMENT '上次巡检时间' AFTER last_check_status,
  ADD COLUMN last_renew_at DATETIME NULL COMMENT '上次自动续期时间' AFTER last_check_at,
  ADD COLUMN check_priority TINYINT NOT NULL DEFAULT 0 COMMENT '巡检插队标记：1=优先检查' AFTER last_renew_at,
  ADD KEY idx_mppl_expire (share_expire_at),
  ADD KEY idx_mppl_check (last_check_at);
```

对应更新 `common/models/material_pool_link.py` 模型与 `common/db/init_database.py` 中的 DDL 镜像。

### 5.2 新表 `xy_share_check_logs`

```sql
CREATE TABLE xy_share_check_logs (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  task_type VARCHAR(20) NOT NULL COMMENT 'renew/check',
  pool_id BIGINT NOT NULL,
  pan_type VARCHAR(20) NOT NULL,
  pan_url VARCHAR(500) NULL,
  old_url VARCHAR(500) NULL,
  result VARCHAR(20) NOT NULL,
  detail TEXT NULL,
  fail_reason VARCHAR(500) NULL,
  duration_seconds FLOAT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_sc_pool (pool_id),
  KEY idx_sc_type_time (task_type, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='网盘分享续期与存活巡检日志';
```

## 7. 异常与风控对策汇总

| 风险 | 对策 |
|---|---|
| 巡检/续期触发网盘风控 | 单批限量、条目间随机 2~3 秒等待、命中风控特征暂停任务 30 分钟并通知 |
| 登录态过期导致大面积误判 | invalid 复查一次才通知；error 永不记为 invalid；通知里附页面特征便于人工甄别 |
| 网盘页面改版导致选择器失效 | error 率突增即告警；日志记录命中选择器，改版后只改选择器常量 |
| 续期中途失败留下新旧地址不一致 | 每条 link 独立提交，失败只影响单条；卡券更新与 link 更新同事务；7 天窗口 + 12 小时轮询保证重试机会 |
| 卡券被人工改过内容 | 仅当卡券仍引用旧地址时才重建，否则跳过并记日志 |

## 8. 落地步骤（三步）

1. **打通卡券联动**：抽 `build_card_text` 到 common；reshare 接入"重建卡券"；加表加字段加日志模型。**此步完成后，手动点重新分享即可自动更新卡券**。
2. **续期任务**：backend-web 内部接口 + scheduler 续期任务 + 注册。
3. **巡检任务**：巡检服务（DrissionPage）+ scheduler 巡检任务 + 插队机制 + 前端日志页 + 通知接入。

每一步都可独立交付、独立验证。
